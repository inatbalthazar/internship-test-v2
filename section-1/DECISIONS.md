D1: Route guard ไว้ตรงไหน
- ทางเลือกที่คิดไว้: (A)component ครอบ route (B)ใช้ loader
- เลือก: A
- เพราะ: redirect ไฟล์เดียว ใช้ซ้ำได้ทั้ง admin และ employee และตัดสินใจก่อน render A เป็น component จึงอ่านผู้ใช้จาก Context ด้วย useAuth ได้ตรงๆ และส่งข้อความแจ้งเตือนไปกับ state ได้ และ loader เกินจำเป็นสำหรับ 3 route
- ข้อเสียของ A ที่ยอมรับ: ข้อความที่ส่งผ่าน location.state ยังค้างอยู่ถ้ากด refresh หน้าปลายทาง ต้องเคลียร์ state เอง

D2: Admin และการจัดการรายการ task
- ทางเลือกที่คิดไว้: (A)mock API เป็นแหล่งข้อมูลที่เดียว แต่ละหน้าเก็บผลที่ดึงมาใน useState และหลังสร้าง Task ก็เอา Task ที่ API คืนมาต่อท้าย (B) เก็บ Task ทั้งหมดใน Context
- เลือก: A
- เพราะ: ทำตัวเหมือนต่อ backend จริง หน้าเว็บไม่แก้ข้อมูลเองโดยไม่ผ่าน API จึงเปลี่ยนเป็น fetch จริงได้โดยไม่ต้องแก้หน้า รายการอัปเดตทันทีโดยไม่ต้องรอโหลดซ้ำ และต่อท้ายเฉพาะเมื่อ API ตอบสำเร็จ หน้าจอจึงไม่แสดง Task ที่บันทึกไม่สำเร็จ
- ข้อเสียของ A ที่ยอมรับ: ข้อมูลอยู่ในหน่วยความจำ กด refresh แล้ว Task ที่สร้างไว้หายกลับเป็น mock เริ่มต้น และถ้าอนาคตมีคนอื่นแก้ข้อมูลพร้อมกัน รายการที่ต่อท้ายเองจะไม่เห็นการเปลี่ยนแปลงของคนอื่น ต้องเปลี่ยนเป็นดึงรายการใหม่ทั้งหมดหลังสร้าง หรือดึงซ้ำเป็นรอบ

D3: Task ของตัวเอง และได้แค่ To Do → Done
- ทางเลือกที่คิดไว้: (A)ซ่อนปุ่มใน UI อย่างเดียว (B)ซ่อนปุ่มใน UI และให้ mock API ตรวจซ้ำ
- เลือก: B
- เพราะ: ซ่อนปุ่มอย่างเดียวไม่พอ ในระบบจริงใครก็ยิง API ตรงได้ กฎจึงต้องอยู่ฝั่ง API ด้วย mock API ทำหน้าที่แทน backend เลยตรวจแบบเดียวกัน
- ข้อเสียของ B ที่ยอมรับ: กฎเขียนสองที่ แต่ฝั่ง UI เช็กแค่ status === "To Do" เพื่อซ่อนปุ่ม กฎเต็มอยู่ใน API 

D4: ตาราง tasks การ assignและ status
- ทางเลือกที่คิดไว้: ผู้รับผิดชอบ (A)คอลัมน์ assigned_to FK ไป users (B) ตารางกลางรองรับหลายคนต่อ task/status (C) VARCHAR + CHECK
- เลือก: A + C
- เพราะ: โจทย์ให้ Task หนึ่งมีผู้รับผิดชอบคนเดียว A จึงพอ และ query หน้า Employee เป็น WHERE assigned_to = ? ตรงๆ ทำ index (assigned_to, status) รองรับการกรองสถานะได้ด้วย ส่วน C กันค่าผิดได้
- ข้อเสียที่ยอมรับ: ถ้าต่อไป Task มีหลายคนรับผิดชอบต้องเปลี่ยนตาราง และกฎ To Do → Done ใส่ใน CHECK ไม่ได้ เพราะ CHECK ไม่รู้ค่าเดิม ต้องตรวจที่ backend

D5: set session token expire
- ทางเลือกที่คิดไว้: (A)เก็บใน Context อย่างเดียว (B)Context + sessionStorage (C)Context + `localStorage`
- เลือก: B
- เพราะ: ตอนทดสอบ guard ต้องพิมพ์ URL เอง ซึ่งทำให้หน้าโหลดใหม่ ถ้าใช้ A จะหลุด login ทุกครั้งและทดสอบกรณี Employee หน้า /admin ไม่ได้ B อยู่ได้จนปิดแท็บ ไม่ค้างนานเท่า C
- ข้อเสียของ B ที่ยอมรับ: แก้ค่าใน sessionStorage ได้ ยอมรับได้เพราะเป็น mock ระบบจริงต้องใช้ jwt ให้ server ตรวจ token
